System Overview RBAC Focus

This page explains how the platform works, especially how RBAC is enforced end-to-end using feature permissions rather than hardcoded role checks.

High-Level Architecture

  • Frontend: apps/web (Next.js UI, route gating, permission-aware components).
  • Backend: apps/api (NestJS + Prisma, authoritative authorization checks).
  • Tokens support frontend routing, but backend permission decisions are always DB-backed through RBAC service checks.

RBAC Data Model

  • SystemFeature: capability keys like finance.invoices, crm.leads, ceo.dashboard.
  • Role: role metadata and default landing path.
  • RolePermission: role-to-feature link with canRead and canWrite.
  • Users inherit feature access through their assigned role.

Authorization Flow

  1. User logs in and backend builds a permission profile from DB.
  2. Access token gets compact permission claim (perms).
  3. API routes are protected with decorators: @RequirePermission(feature, action) or @AllowAuthenticated().
  4. PermissionGuard enforces fail-closed policy (no policy, no access).
  5. RbacService.can(userId, feature, action) validates effective permission from DB-backed role data.

Frontend Route Gating

  • Middleware decodes token claims and expands compact perms into a permission map.
  • Route checks and landing resolution are feature/module based and fail closed when permissions are missing.
  • If permission data is unavailable in token, user is redirected to re-authenticate.

Security Principles

  • No hardcoded role bypasses for authorization decisions.
  • Feature permissions are centrally seeded and role-attached.
  • Auth cookies are httpOnly and secure in production.
  • JWT strategy re-validates user activity/deletion status each request.
  • Sensitive responses use safe field selection.

How to Read the Module Guides Below

Each module below lists every SystemFeature permission key, what it unlocks in the UI, and — the important part — which other permissions must be granted alongside it for the feature to actually work end to end.

  • Unlocks: the page/action this permission's canRead/canWrite gates directly (sidebar link, API endpoint, or both).
  • Also grant: a companion permission (usually read-only) needed because the page fetches data owned by a different feature — e.g. a picker/dropdown, a linked record, or a lookup the form needs before it can be submitted. The API endpoint for the permission itself doesn't require this — the UI silently breaks without it (empty dropdown, dead link, "failed to load", or a 403 toast on submit after everything looked fine).
  • A — none — entry means the feature is self-contained: nothing else to grant.
Rule of thumb: when creating a custom role, grant read on every permission referenced in the "Also grant" column for every feature you give write on. Missing one doesn't break the API — it breaks the form silently (empty picker, blank card, or a submit button that 403s).

IT

PermissionUnlocksAlso grantWhy
it.users User list, create, deactivate, change role it.roles (r) Both "Create User" and "Change Role" populate their role dropdown from the Roles API — without it, no role can be selected.
it.roles Create/rename/delete roles, view role list it.permissions (r) to view the feature matrix, (w) to save it Important split: the role editor's permission checkboxes save via a separate endpoint gated by it.permissions write, not it.roles write. A role with only it.roles write sees a fully interactive checkbox matrix that 403s on Save — a role it creates starts with zero feature grants and can't be given any.

it.audit IT change audit trail — none — Self-contained.
The IT sidebar shows all four links to anyone with any it.* permission (a module-level check, not per-link), and the Roles/Users list pages swallow 403s into an empty list rather than showing an error. A user missing the right companion permission sees "no data" instead of "access denied" — worth explaining to anyone troubleshooting a custom IT role.

CEO

PermissionUnlocksAlso grantWhy
ceo.dashboard The entire executive /ceo dashboard — none — Self-contained by design — see note below.

How "the CEO sees everything" actually works: it's neither a permission bypass nor per-module composition. The dashboard is a dedicated read-model — its single backing endpoint runs its own aggregate queries directly against Finance, CRM, HR, Projects, Ventures, and every service module's data, gated by exactly one permission: ceo.dashboard read. It never calls the other modules' guarded endpoints, so no other permission is ever evaluated in that code path — it would render fully for a hypothetical role holding only ceo.dashboard. Separately, the seeded CEO role is also granted full read+write on every system feature, which is what lets a CEO click into Finance/CRM/HR/Projects pages themselves (each independently gated) — that grant is unrelated to how the dashboard itself works.
