System Overview RBAC Focus

This page explains how the platform works, especially how RBAC is enforced end-to-end using feature permissions rather than hardcoded role checks.

High-Level Architecture

  • Frontend: apps/web (Next.js UI, route gating, permission-aware components).
  • Backend: apps/api (NestJS + Prisma, authoritative authorization checks).
  • Tokens support frontend routing, but backend permission decisions are always DB-backed through RBAC service checks.

RBAC Data Model

  • SystemFeature: capability keys like finance.invoices, crm.leads, ceo.dashboard.
  • Role: role metadata and default landing path.
  • RolePermission: role-to-feature link with canRead and canWrite.
  • Users inherit feature access through their assigned role.

Authorization Flow

  1. User logs in and backend builds a permission profile from DB.
  2. Access token gets compact permission claim (perms).
  3. API routes are protected with decorators: @RequirePermission(feature, action) or @AllowAuthenticated().
  4. PermissionGuard enforces fail-closed policy (no policy, no access).
  5. RbacService.can(userId, feature, action) validates effective permission from DB-backed role data.

Frontend Route Gating

  • Middleware decodes token claims and expands compact perms into a permission map.
  • Route checks and landing resolution are feature/module based and fail closed when permissions are missing.
  • If permission data is unavailable in token, user is redirected to re-authenticate.

Security Principles

  • No hardcoded role bypasses for authorization decisions.
  • Feature permissions are centrally seeded and role-attached.
  • Auth cookies are httpOnly and secure in production.
  • JWT strategy re-validates user activity/deletion status each request.
  • Sensitive responses use safe field selection.

How to Read the Module Guides Below

Each module below lists every SystemFeature permission key, what it unlocks in the UI, and — the important part — which other permissions must be granted alongside it for the feature to actually work end to end.

  • Unlocks: the page/action this permission's canRead/canWrite gates directly (sidebar link, API endpoint, or both).
  • Also grant: a companion permission (usually read-only) needed because the page fetches data owned by a different feature — e.g. a picker/dropdown, a linked record, or a lookup the form needs before it can be submitted. The API endpoint for the permission itself doesn't require this — the UI silently breaks without it (empty dropdown, dead link, "failed to load", or a 403 toast on submit after everything looked fine).
  • A — none — entry means the feature is self-contained: nothing else to grant.
Rule of thumb: when creating a custom role, grant read on every permission referenced in the "Also grant" column for every feature you give write on. Missing one doesn't break the API — it breaks the form silently (empty picker, blank card, or a submit button that 403s).

Invoices

Draft
An invoice created but not yet sent to the client. It has no due-date pressure and can't receive payments until it's sent.
Sent
The invoice has been issued to the client and is now awaiting payment.
Partially Paid
One or more payments have been recorded against the invoice, but the total paid is still less than the invoice total.
Paid
The sum of all recorded payments meets or exceeds the invoice total; the system stamps a paid date automatically.
Overdue
A nightly automated job flips any Sent or Partially Paid invoice whose due date has passed into Overdue and notifies Finance Managers — nobody has to do this by hand.
Written Off
A Finance user gives up on collecting an invoice (client dispute, insolvency, etc.). Only Sent, Partially Paid, or Overdue invoices can be written off; doing so locks it from further payments and alerts the CEO.
Write-off Category
The reason tag recorded on a write-off: Client Dispute, Client Insolvent, Agreed Write-off, Uncollectable, or Other.
Credit Note
A document that reduces or refunds part of an already-issued invoice (e.g. an overcharge or agreed discount). Moves through Issued → Refund Pending → Refund Paid, or can be Voided.
Payment Plan
An agreement to split one invoice's balance into instalments, each with its own due date and status. The plan itself is Active, Completed, or Cancelled.

AR & Cash

MTD (Month-to-Date)
The period from the 1st day of the current calendar month up to now — used consistently across every finance dashboard figure.
AR / Outstanding AR
The total still owed across all Sent, Partially Paid, and Overdue invoices (each invoice's total minus payments already recorded against it). Draft, Paid, and Written-off invoices never count.
Revenue / Invoiced
The total value of invoices created within a given period, regardless of whether they've been paid yet.
Collected
Actual cash received — the sum of Payment records recorded in the period, not just invoiced amounts.
Income
Collected payments plus Direct Income for the period — the all-in "money that actually came in" figure.
Direct Income
Money logged as received without ever raising an invoice (e.g. a walk-in cash sale), recorded with its own payment method and reference.
Bank Reconciliation
Uploading a bank statement and matching each line to a Payment or Expense already in the system. A statement run is In Progress, Completed, or ends in Discrepancy if things don't line up.
Matched Transaction
Each bank statement line is auto-matched or left Unmatched; an unmatched line can be manually linked to an existing payment/expense (Manually Resolved) or dismissed as irrelevant (Ignored).
Reserve Fund
A company savings account topped up or drawn down only by manual Deposit/Withdrawal entries — not an automatic percentage of revenue. A deposit also logs an expense; a withdrawal also logs direct income.
Bills & Payables
Money the company owes to vendors/suppliers. A Bill starts Unpaid, becomes Partially Paid or Paid as it's settled.

Ventures & Commissions

Venture
A distinct business line or brand under the company. Clients, invoices, expenses, income entries, retainers, and leads can each be tagged to a venture to track that business line's numbers separately from the company as a whole.
Tagging a client to a venture
Assigning a venture to a client record so all of that client's activity rolls up under the venture's reporting.
Commission Rule
A standing percentage rate set for a specific sales agent (optionally per service type), used to calculate commissions on future deals.
Commission Record
The actual commission earned on one closed deal, calculated from the matching rule and moved through Pending → Approved/Rejected → Paid by a manager. Amounts can be manually adjusted with a reason.
"Own" commissions vs. all
Agents with the narrower commissions permission can only view/manage their own commission records; a separate, broader permission is needed to see every agent's commissions.

Recurring Billing

Retainer (Retainer Contract)
A recurring service agreement with a client for a fixed monthly amount, billed automatically on a set day of the month. Statuses: Draft, Active, Paused, or Ended. Supports extensions that change its end date/amount.
MRR (Monthly Recurring Revenue)
The sum of the monthly amount of every currently Active retainer contract — a snapshot of guaranteed recurring billing, not actual cash collected.

Compliance & Tax

Tax Rate
A configured percentage (by country and optionally service type) applied to invoices and retainers when calculating tax.
Tax Owed / Liability
For the current month: the tax portion of all invoices marked Paid, minus whatever has already been remitted to tax authorities in overlapping periods. A positive number means money is still owed.
Tax Remittance
A record of an actual payment made to a tax authority for a given period, used to offset the computed tax liability.
Budget (Project Budget)
The approved spending ceiling for a project. Tracks an alert threshold percentage and can automatically block further spending once exceeded, with its own approval workflow (Pending/Approved/Rejected) for requests to increase it.

Payroll

Payroll Run
One month's payroll batch, moving from Draft (editable) to Processed (calculated, employees paid) to Locked (frozen — can no longer be edited or deleted).
Payslip
The per-employee breakdown within a run (base salary, commission, bonus, deductions, net pay), which can be emailed to the employee once generated.
Second Approver
An optional employee designated in Finance Settings to review/process a payroll run — the run's creator is not allowed to process their own run, so a second person must be involved.

CRM Core

Lead
A prospective deal captured with contact info, an estimated value, and a source. Whether it's a "venture-type" or "service-type" lead depends on whether a Venture was picked (venture-type) or it's classified by a free-text service interest instead (service-type).
Proposal
A priced offer sent to a lead, moving through Draft → Sent → Accepted/Rejected/Expired.
Client (CRM)
A converted, ongoing business relationship record with a source (how they became a client: Pipeline, Direct, Referral, Returning) and a primary service that drives which service module gets set up for them.
"CRM — View All Records"
Not a separate feature or page — a permission that switches a user's CRM views from "my assigned records only" to "every record in the CRM."
Venture (CRM link)
Leads and clients can be tagged to a Venture so revenue (invoices, retainers, commissions) is attributed to that specific business line rather than the company as a whole.

Pipeline & Deals

Pipeline stage
A lead's position in the sales journey: New → Contacted → Proposal Sent → Negotiation → Closed Won/Closed Lost.
Sending a proposal
Auto-advances the lead from New/Contacted to Proposal Sent.
Accepting a proposal
Auto-advances the lead to Negotiation — not straight to Closed Won — and notifies the owner to close the deal manually.
Closed Won
Moving a lead here requires choosing an outcome (invoice or retainer). It auto-creates or links a Client, calculates the rep's commission, and either drafts a Retainer Contract or sets up the matching service record (software project, branding project, marketing/influencer campaign, etc.) depending on whether the lead was venture-tagged or service-tagged.
Closed Lost
Requires a reason, is terminal, and cannot be moved again.
Conversion Rate / Funnel
The share of leads that end Closed Won vs. Closed Lost within a date range, plus stage-by-stage counts, average deal value, and average days-to-close.

Sales

Sales Campaign (field sales)
A territory/product outreach effort tied to a Client, with a start/end date and status Active/Completed/On Hold/Cancelled.
Deploy Agent
Assigning an HR employee to an active Sales Campaign as a field sales agent, with visit/lead/sales targets. Fails if the campaign isn't active or the employee is already deployed.
Campaign completion
Marking a campaign Completed auto-generates a draft invoice for Finance to review if a total cost was set, and notifies the Finance Manager.

Marketing

Marketing Client
A distinct record — not the same as a CRM Client — created only against an existing, active finance Retainer Contract. You must pick a retainer; it fails if the retainer isn't active or is already linked to another marketing client.
Retainer (marketing context)
The underlying recurring-billing contract in Finance that a Marketing Client is anchored to — it defines the service and billing amount being fulfilled.
Content item
A single scheduled social/marketing post belonging to a Marketing Client, moving Draft → Ready → Approved → Published, with Rejected and Cancelled as side branches.

Influencer

Influencer
A database entry for a content creator: name, handle, primary platform (plus other platforms), follower count, category, and contact info.
Influencer Campaign
An Active/Completed/On Hold/Cancelled effort for a Client with a budget that, once set, auto-generates a draft invoice for Finance.
Assign
Attaching an influencer to an active campaign with an agreed fee and one or more deliverables.
Verify (a deliverable)
Confirming the influencer actually posted the required content, stamping who verified it and when. A verified deliverable blocks removing that influencer from the campaign.
Pay
Logging a one-time payment to an influencer, which also books an expense in Finance and marks the assignment paid.
Complete (campaign)
Closes out the campaign and warns if any deliverables are still unverified or influencers unpaid.

HR

Attendance vs. Leave
Two separate features sharing one permission. Attendance is a daily check-in/check-out log with statuses Present, Absent, Half Day, On Leave, Public Holiday, Weekend. Leave is a separate request-and-approval workflow against a yearly entitlement.
Leave Type
A configurable category of leave (e.g. Annual, Sick) defining default days/year, whether it's paid, and whether it needs approval or a supporting document.
Leave Balance
An employee's entitlement for a given year and leave type: days entitled, used, pending approval, remaining, and carried over from the prior year.
Leave Request
An employee's application for time off, moving Pending → Approved/Rejected/Cancelled.
Leave Year
An HR-wide setting defining when annual leave entitlements reset (default January 1st).
Performance Review
A structured review cycle per employee/period: Draft → Self-Assessment → Manager Review → Acknowledged → Completed. A manager initiates it, the employee completes a self-assessment, the manager adds notes/rating, then the employee acknowledges it.
Onboarding Checklist
A per-employee list of onboarding tasks (category, due date, completion) tracked as In Progress, Completed, or Overdue.
Sensitive Employee Data
The fields hidden unless a role has the sensitive-data permission: salary, salary effective date, national ID, bank name/account, emergency contact, and notes.
HR Payroll
A read/adjust view of an employee's own salary history shown on their profile — not a payroll engine, just visibility into pay changes over time. Distinct from Finance's Payroll Run, which is the actual payroll engine.
HR Audit Log
A record of every create/update on HR data (who, what field changed, old/new value) for compliance.

Projects

Project
A client engagement running Active → On Hold/Completed/Cancelled/Archived, owned by a manager, with milestones, tasks, members, and files.
Milestone
A named phase/checkpoint of a project (Pending → In Progress → Completed) that groups tasks and is marked complete via its own action.
Task
A unit of work under a project (optionally under a milestone), moving To Do → In Progress/Blocked/In Review → Done, with priority, assignee, due date, and comments.
CSV Task Import
A bulk-upload feature that creates many tasks at once from an uploaded CSV file.
Status Report
An on-demand, real-time snapshot of a project's health: overall progress, recent activity, tasks due in the next 14 days, and currently blocked tasks. Computed live, not stored.
Handover Report
A one-time, permanently saved summary generated only after a project reaches Completed — covering final deliverables, milestones/tasks, approved client deliverables, files, cost, and duration.
Approval (Deliverable Approval)
The review of a specific task's deliverable (a file/description submitted for sign-off) — not the milestone itself. A manager/client approves or rejects with a required note on rejection; approving an approval-gated task auto-marks it Done.
All Projects vs. Own Projects
"All Projects" is the company-wide project-management view (create/edit any project, milestones, approvals). "Own Projects" restricts a user to projects/tasks they're a member of or assigned to — "my work across all my projects."

IT / RBAC Core Concepts

Feature
The smallest permission unit in the system, e.g. hr.payroll or projects.all. Every feature belongs to exactly one Module.
Permission
The read/write grant a Role has on one Feature — stored as a read flag and a write flag.
Role
A named bundle of permissions (e.g. "HR Manager") assigned to users. A role links to many features, each with its own read/write flags — Role → Permission → Feature is the full chain that decides what a user can see and do.
Module
A top-level app section (finance, hr, projects, it, crm, etc.). Every feature is tagged with exactly one module, which is how the UI groups permissions and navigation.
Home Module
A field on a Role (default Finance) that determines the page a user lands on immediately after logging in.
IT Audit Log
A record of RBAC/user-management actions: role created/updated/deleted, bulk permission updates, and user created/role-changed/deactivated/activated, each with before/after values.

Software Delivery

Software Project (phase)
A dev engagement that moves through a fixed phase sequence: Requirements → Design → Development → QA → Deployment → Maintenance → Completed, each phase backed by its own panel rather than one shared workflow.
Requirements
Versioned requirement documents drafted, sent to the client, and signed off (Draft → Sent → Signed/Revised).
Design (phase)
A Figma-linked design stage that can be skipped, sent to the client, approved, or sent back with changes requested.
Sprint
A fixed-date development iteration (name, goal, start/end date) that goes Planned → Active → Completed/Skipped and contains its own items (title, assignee, story points, status).
QA
A bug-tracking phase (skippable) holding bug records with severity (Critical/High/Medium/Low) and status (Open/In Progress/Resolved/Won't Fix).
Deployment
The record of go-live: when it was deployed, the URL, server details, and who deployed it.
Maintenance
Post-launch issue tracking (bug/update/security) logged until the maintenance window ends.

Branding Delivery

Branding Project
A client branding engagement (In Progress → Delivered/On Hold/Cancelled) made up of individual scope items.
Scope Item
One deliverable within a branding project (e.g. "logo design"), optionally assigned to a supplier, tracked In Progress → Submitted → Approved/Rejected → Delivered.
Supplier
An external vendor/contractor who can be assigned to fulfill a scope item.
Design Submission
A versioned file submitted against a scope item for client review, going Pending → Approved/Rejected with optional client feedback — this drives the parent scope item's own status forward.

Finance & Ventures

How It Works

  1. Overdue invoices flip automatically. A daily job at 8:00 AM finds every Sent or Partially Paid invoice whose due date has passed, bulk-flips it to Overdue, and notifies Finance Managers — nobody marks an invoice overdue by hand.
  2. Retainers bill themselves. A separate daily job at 7:00 AM finds every Active retainer whose next billing date has arrived, generates and emails an invoice (30-day due date, tax computed from the retainer's tax rate), then advances its next billing date. If a billing day (e.g. the 31st) doesn't exist in the target month, it clamps to that month's last day instead of skipping or erroring. If generation fails for one retainer, that one is logged as an error and simply retried the next day — it doesn't stop the rest of the batch.
  3. Payroll gross pay reflects commissions as of processing, not as of the run's creation. Creating a Draft payroll run sums each agent's currently Approved commissions for that month as an initial estimate for the line items. Right before a run is actually processed, every line item that a manager hasn't manually adjusted is re-synced against whatever commissions are Approved for that agent/month at that moment — so a commission approved any time after the run was drafted but before it's processed still gets included in gross pay, and is marked Paid consistently with what was actually paid out. A line item a manager has manually overridden is left untouched — the override is authoritative and isn't re-synced.
  4. Processing a Draft run generates and emails each employee's payslip, flips their eligible commissions to Paid, and books two P&L expenses automatically: one Staff expense (base salary + bonus, summed across the run) and one Commission expense (commission, summed across the run) — both tagged back to the run. Net pay is gross − (gross × tax rate) − other deductions, where gross is base salary + commission + bonus. The run then moves Draft → Processed, and can optionally be Locked afterward — a Locked run can no longer be adjusted or deleted, making it the permanent record of what was actually paid.
  5. A venture's income/expense numbers are computed live, not stored: income is Paid invoices (by paid date) plus Direct Income entries in the period; expenses are every Expense tagged to that venture, each counted at its individual venture-share percentage (not necessarily 100%) — net profit is simply income minus that share of expenses.
  6. Bank reconciliation auto-matches on amount + date. After a statement import, every unmatched line is checked against Payments (for money in) or Expenses (for money out) for an exact amount match within 2 days of the transaction date. Anything that doesn't find an exact match stays Unmatched for a human to resolve manually — there's no fuzzy or partial-amount matching.
  7. Tax owed is simply tax collected on Paid invoices this period − tax already remitted (input tax tracking isn't implemented, so it's always treated as zero) — a positive result means money is still owed to the tax authority.

CRM

How It Works

  1. A lead defaults to its creator. If nobody is explicitly assigned when a lead is created, the system assigns it to whoever created it — so every lead always has an owner, and that owner can earn commission on it. Leaving a lead genuinely unowned isn't possible.
  2. Pipeline stage moves in order: New → Contacted → Proposal Sent → Negotiation → Closed Won/Closed Lost. Sending a proposal auto-advances the lead to Proposal Sent; the client accepting that proposal auto-advances it to Negotiation — deliberately not straight to Closed Won — and notifies the owner to close the deal manually. Closed Lost requires a reason and is terminal; nothing can be moved again after it.
  3. Closing a deal is the biggest single action in CRM. Moving a lead to Closed Won requires entering the final deal value (it doesn't have to match the original estimate) and, optionally, correcting the client/contact info in the same step. That single action then: creates a new Client record or links to a matching existing one (syncing company/contact/phone onto an existing match, but never overwriting its email, since email is part of how the match is found); calculates the rep's commission from the final deal value and their commission rule; and either drafts a Retainer Contract or sets up the matching delivery record (software project, branding project, marketing/influencer campaign) depending on whether the lead was venture-tagged or service-tagged.
  4. Commission calculation: the system looks up a standing Commission Rule for that agent — a service-specific rule first, falling back to the agent's catch-all rule if one exists — and computes final deal value × rate% ⁄ 100. If no matching rule exists at all, no commission record is created for that deal. The resulting record starts Pending, and a manager moves it Approved/Rejected (amounts can be manually adjusted with a reason before approval); it's only marked Paid automatically when that agent's payroll for the month is processed — see Finance for the timing gap that creates.
"View All Records" is a pure scope switch. Agents without crm.all only ever see leads/pipeline items/ proposals they own — this filtering happens on every list query, not just the UI. crm.clients has no such owner filter (everyone with client read sees every client), and crm.reports is always company-wide regardless of crm.all.

Sales

How It Works

  1. A Sales Campaign is created against an existing CRM client with a start/end date; it starts Active.
  2. Deploying an agent attaches an HR employee to an Active campaign with visit/lead/sales targets — it's blocked if the campaign isn't Active or if that employee is already deployed to it.
  3. Marking a campaign Completed auto-generates a Draft invoice in Finance if the campaign had a total cost set, and notifies the Finance Manager to review and send it — field sales revenue doesn't need a separate manual invoicing step.

HR

How It Works

  1. Onboarding is automatic, not a separate step. Creating an employee record immediately creates a LeaveBalance row for every active leave type and auto-generates an Onboarding Checklist with 12 fixed default items across four categories (Documentation, IT Setup, Team Introduction, Training), each with a due date offset from the employee's start date. There's no "start onboarding" action and the list isn't customizable per hire. When the last item is checked off, the checklist auto-flips to Completed.
  2. Attendance is self-service check-in/check-out. An employee checks in (creates today's record, status Present) and checks out (computes working hours; under 4 hours auto-downgrades the record to Half Day). Checking in twice in a day is blocked.
  3. Leave requests reduce the visible balance immediately on submission, not on approval. Balance is recalculated from scratch as entitled + carryOver − sum(approved) − sum(pending) every time a request is submitted, approved, rejected, or cancelled — so a Pending request already eats into "remaining" days, and rejecting or cancelling one restores the balance automatically. Overlapping Pending/Approved requests for the same employee are blocked at submission.
  4. Performance reviews move Draft → Manager Review → Acknowledged → Completed: a reviewer opens the cycle, the employee submits a self-assessment (jumping straight to Manager Review), the manager rates 1–5 and adds notes (only possible while the review is exactly in Manager Review), then the employee acknowledges it to close it out. Each step notifies the next person in the chain.
  5. Sensitive fields are filtered in the service layer, not hidden by CSS or blocked by a route. Every employee list/detail response checks hr.employees.sensitive read per request; without it, salary, salary effective date, national ID, bank details, emergency contact, and notes are stripped from the JSON entirely before it leaves the server — even an employee viewing their own profile never gets these fields back from that endpoint.
Settings that don't do anything yet: HR Settings lets you configure working_days, working_hours_per_day, leave_year_start, carry_over_max_days, and probation_days — but none of them are read anywhere else in the system. Leave-day counting hardcodes Mon–Fri, leave balances are always keyed to the calendar year with no rollover job, and there's no probation logic. They're stored and editable, but currently cosmetic — don't assume changing them changes behavior.

Projects

How It Works

  1. Creating a project can spin up a second record. If the service type is software development, a client is mandatory and the system automatically creates a linked Software Project in the Software module in the same action. Every new project starts Active — there's no draft state — the manager is auto-added as a project member, and if a total cost and client are set, a Draft invoice is generated in the background.
  2. Status moves: Active ⇄ On Hold, Active → Completed, and anything → Archived (archiving has no status guard — it works from any state). Completing a project is a soft gate, not a hard block: if any task isn't Done, the API refuses — unless the request explicitly passes "acknowledge incomplete tasks," which overrides it. So a PM can knowingly close a project with loose ends.
  3. Milestones are gated more strictly than projects. A milestone can only be marked Completed once every task under it is Done — there is no override/acknowledge flag here, unlike project completion.
  4. Tasks track every status change in a TaskStatusHistory audit trail. Status transitions are unrestricted (any status → any other), but moving a task to Blocked automatically notifies the project manager. CSV import expects columns title, description, milestoneName, assigneeEmail, priority, dueDate, estimatedHours — only the title is required; unmatched milestone names or assignee emails don't fail the row, they just import without that link and surface a per-row error in the response.
  5. Deliverable Approvals are tied to a specific task, not the milestone. Requesting approval notifies the project manager (approval is manager-facing, not client-facing, in this build). Rejecting requires a note and sets the task's approval status to "changes requested" — the task's own status/board column is untouched. Approving a task that was flagged "requires approval" auto-marks that task Done — approving a task that wasn't flagged that way only updates the approval record, not the task status.
  6. Status Report vs. Handover Report: the Status Report is computed fresh on every page load (progress %, tasks due in 14 days, blocked tasks, recent activity) — nothing is saved. The Handover Report can only be generated once a project is Completed; it's built once and permanently saved, and later visits just re-fetch that saved snapshot rather than recomputing it.
  7. Project Budget is one-to-one with a project. A daily background job compares total tagged expenses against the approved budget: at or above the alert threshold (default 80%) it notifies Operations Managers (at most once every 7 days); over 100% it automatically blocks the budget. A blocked budget only stops new expenses from being logged against that project — it doesn't touch tasks or invoices. Unblocking requires a Budget Increase Request to be approved, which raises the ceiling and lifts the block in the same action.

IT

How It Works

  1. Creating a role is two separate write actions. "New Role" only inserts a bare role row — it grants nothing on its own. Saving the permission matrix on that role's detail page is a second call gated by a different permission (it.permissions write). A role sits with zero feature access between those two steps.
  2. Permission changes take effect within one request — no re-login needed. Every guarded API call re-checks the caller's effective permission straight from the database, backed by a short-lived (5 minute) server-side cache keyed per user. Editing a role's permissions or reassigning a user to a different role immediately clears that user's cache entry, so the very next API call already sees the new permissions.
  3. The JWT's permission claim is a UI convenience, not the source of truth. The access token does carry an encoded permission snapshot (used by frontend route gating), but the backend never reads it to authorize a request — only the DB-backed check above does. That means the API enforces new permissions instantly, while the frontend's own menu/route gating can lag until the user's token next refreshes.
  4. Deactivating or role-changing the last active IT Administrator is blocked outright — the system will not let you strand the account with nobody left to administer it.
The permission cache is an in-process memory store, not a shared cache like Redis. In a multi-instance deployment, invalidating it on one instance doesn't clear it on the others — they'd keep serving the old permission set to already-connected users for up to 5 minutes after a change.

The IT sidebar shows all four links to anyone with any it.* permission (a module-level check, not per-link), and the Roles/Users list pages swallow 403s into an empty list rather than showing an error. A user missing the right companion permission sees "no data" instead of "access denied" — worth explaining to anyone troubleshooting a custom IT role.

Software

How It Works

  1. A software project moves through a fixed phase sequence — Requirements → Design → Development → QA → Deployment → Maintenance — advanced manually by a delivery lead clicking "Advance Phase," not automatically.
  2. Each phase gates the next one differently: leaving Requirements needs at least one requirements document signed by the client; leaving Development needs the current sprint to be Completed (not still Active); leaving QA needs zero unresolved Critical bugs (unless QA is explicitly marked skipped). Leaving Design has no enforced gate — an unapproved design doesn't block advancing past it.
  3. Deployment is the one exception to manual advancement: recording a Deployment automatically jumps the project straight to Maintenance as a side effect, and sets the maintenance window to end exactly one year later. There's no built-in action that ever moves a project from Maintenance to Completed.
  4. Sprints only allow one Active sprint per project at a time — starting a new one is blocked while another is already Active. Sprint Items (the tasks inside a sprint board) are a completely separate model from the general Project task system — they don't sync, link, or share any data with regular Tasks.

Since the whole /software/* route (including detail pages) is gated on software.projects, Team Members are redirected away before ever reaching the panels their own permission unlocks.

Branding

How It Works

  1. A branding project is made up of individual Scope Items (e.g. "logo design"), each moving In Progress → Submitted → Approved/Rejected → Delivered independently — there's no overall project-status gate blocking work on any one item.
  2. Submitting a design creates a versioned Design Submission against a scope item. If that scope item already has a submission awaiting review, submitting a new version automatically supersedes the old one (auto-rejects it with a "superseded by new version" note) rather than leaving two pending reviews stacked up.
  3. Client review approves or rejects a submission — rejection requires written feedback. On rejection, the designer simply submits again against the same scope item; the next submission bumps the version number and puts the scope item back to Submitted. There's no separate "revision request" object — it's the same submit/review loop.
  4. "Deliver" doesn't require every item to be approved first. Marking a project delivered bulk-moves every currently Approved scope item to Delivered — any items that aren't approved yet are simply left behind, with a warning listing how many were skipped, rather than blocking the whole action.
  5. A Supplier can only be assigned to a scope item at the moment it's created — there's no way to change or add a supplier to an existing scope item afterward. Supplier assignment is a pure label: it doesn't change the approval flow or gate anything differently from internally-produced work.

Influencer

How It Works

  1. An Influencer Campaign is created against a client; setting its budget automatically generates a Draft invoice in Finance, the same auto-invoicing pattern used by Sales campaigns.
  2. Assigning an influencer to an active campaign records an agreed fee and one or more deliverables (specific content the influencer owes, e.g. one Reel + two Stories).
  3. Verifying a deliverable confirms the influencer actually posted the required content and stamps who verified it and when. Once at least one deliverable on an assignment is verified, that influencer can no longer be removed from the campaign — it locks the assignment in place rather than letting a verified collaboration disappear.
  4. Paying an influencer logs a one-time payment that simultaneously books an Expense in Finance and marks the assignment as paid — same pattern as the payroll flow, one action updates both modules.
  5. Completing a campaign doesn't block on loose ends — it warns if any deliverables are still unverified or any influencers still unpaid, but lets the manager close it out anyway.

Marketing

How It Works

  1. A Marketing Client can only exist on top of an active Retainer. Creating one requires picking an existing, Active finance Retainer Contract — it's rejected outright if the retainer isn't active or is already linked to a different marketing client. This is what defines the marketing client's service scope and billing amount; the marketing client itself is a separate record from the CRM Client.
  2. Content items move Draft → Ready → Approved → Published, with Rejected and Cancelled as side branches at various points — each scheduled post belongs to one Marketing Client and carries its own content type (Post, Reel, Story, Carousel, Video, Blog, Email, or Ad).
  3. The content calendar has two views. Per-client calendars live on each marketing client's page; a global calendar aggregates every client's scheduled content into one view so nobody has to click through clients one at a time to see the week's full schedule.
  4. PDF export is week-scoped. Downloading a calendar (either a single client's or the global one) opens a week picker; the generated PDF's filename embeds the ISO week number and the exact date range covered, so downloaded files from different weeks never collide or get confused with each other.

CEO

How It Works

The dashboard's venture income/expense cards read the same underlying data as the Ventures module itself: income is Paid invoices (by paid date) plus Direct Income for the period, and expenses are each venture-tagged Expense counted at its own venture-share percentage — so the CEO dashboard and a venture's own detail page always agree with each other, because they're computed the same way rather than two parallel implementations.

PermissionUnlocksAlso grantWhy
ceo.dashboard The entire executive /ceo dashboard — none — Self-contained by design — see note below.

How "the CEO sees everything" actually works: it's neither a permission bypass nor per-module composition. The dashboard is a dedicated read-model — its single backing endpoint runs its own aggregate queries directly against Finance, CRM, HR, Projects, Ventures, and every service module's data, gated by exactly one permission: ceo.dashboard read. It never calls the other modules' guarded endpoints, so no other permission is ever evaluated in that code path — it would render fully for a hypothetical role holding only ceo.dashboard. Separately, the seeded CEO role is also granted full read+write on every system feature, which is what lets a CEO click into Finance/CRM/HR/Projects pages themselves (each independently gated) — that grant is unrelated to how the dashboard itself works.
